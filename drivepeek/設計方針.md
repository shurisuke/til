# DrivePeek設計方針

## 概要
DrivePeekは「地図検索・AI提案・コミュニティのおすすめからドライブプランを作成・共有する」サービス。
Google Mapsと連携したルートプランニングを実現している。

### 技術スタック
- **バックエンド**: Ruby 3.2.2, Rails 8.1, PostgreSQL
- **フロントエンド**: Hotwire (Turbo + Stimulus), Bootstrap 5, SCSS with Importmap
- **外部サービス**: Google Maps APIs (JavaScript, Places, Directions), OpenAI API
- **インフラ**: Render, GitHub Actions CI/CD (RSpec, RuboCop, Brakeman), Solid Queue/Cache
- **品質**: 652テスト通過, 98.26%カバレッジ

## 設計のポイント

### 1. Rails規約優先・シンプル設計
- コントローラは薄く、実ロジックはモデルへ
- 巨大Service禁止 / `Service#call`禁止（意図が伝わるメソッド名を使用）
- DHH的思考：「Railsの規約で素直に書けるか」を優先し、過剰な抽象化・設定・汎用化はしない

### 2. Hotwire設計方針
- **サーバーがUI状態を決定し、StimulusはUI表示制御・API通信に徹する**
- innerHTML書き換えより`hidden`属性、直接DOM操作よりイベント経由
- **CSSで一括制御**: 複数要素の表示切替は`body`クラス + CSSで制御（JSで個別操作しない）
  - 例: `body.area-draw-active` → CSSで関連要素を一括非表示

### 3. Stimulusディレクトリ構成
- 機能ドメインごとにディレクトリを分け、横断UIは`ui/`に集約
  - `plan_tab/`, `community_tab/`, `suggestion_tab/` — タブ固有
  - `infowindow/` — InfoWindow固有
  - `ui/` — 横断的な共通UI
- **HTML**: 構造・選択肢・初期状態の定義（サーバーサイドで生成）
- **JS**: 表示制御・API通信のみ（HTMLの動的生成は避ける）

### 4. 3層AI提案設計
AI任せにせず、処理を3層に分離してハルシネーションを削減：
1. **ユーザー入力層**: 地図上でのエリア描画、ジャンル選択
2. **データベースフィルタリング**: 不適切な施設（ホテル、コンビニ等）の除外、お気に入り順ランキング
3. **AI精査**: 季節適合性、ドライブ適性の評価

### 5. ルート計算とスケジュール計算の分離
- `Plan::Driving`と`Plan::Timetable`を分離してAPIコール最小化
- ルート再計算: スポット追加/削除/並び替え時のみDirections APIを使用
- スケジュール更新: キャッシュデータを使用（コスト削減・レスポンス向上）

### 6. サーバードリブンUI（Google Maps連携）
- InfoWindowのHTMLをJavaScriptで構築せず、Turbo Framesでサーバーから取得
- Rails内でロジックを統一しながら、インタラクティブな地図機能を維持

## 技術的な決定事項

### 再利用・統合優先
- 新規ファイル作成は強い正当化が必要
- 既存コード参照が必須
- 作成よりも再利用を優先

### 実装前ドキュメント作成
- 実装開始前に`docs/tasks/issue-<issue番号>-plan.md`に実装計画を作成
- 内容: 概要、影響範囲、実装詳細、技術的ポイント、検証項目

### Git運用
- mainブランチへの直接プッシュ禁止（フィーチャーブランチ + PR経由）
- コミットメッセージ形式: `<type>: <内容> (#<issue番号>)`
- 1ブランチ = 1PRの原則
